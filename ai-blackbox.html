02The input contract

Five input channels. Each has a defined shape so the agents know exactly what to consume and where it lands in the outputs. Nothing else is required — the engine researches the rest.

1 · Instructions

The brief

Free-text goals + scope + tone + any hard constraints.

  • Objective ("sell an Odoo overhaul", "due-diligence pack", "investor teaser")
  • Deliverable scope & depth, audience, language(s)
  • Guardrails: what must not appear (e.g. "no peso valuation estimates")
  • Section emphasis & ordering preferences
brief.md · plain language · iteratively refinable
2 · Odoo credentials

The build target

Where the live demo gets built. Handled as a runtime secret.

  • url — instance, e.g. https://acme.odoo.com
  • db — database name
  • api_key / login — used only for XML-RPC / MCP at runtime
  • Optional: which apps/industries to activate (e.g. Hotel)
secret · never written to the repo · rotate after
3 · Google Drive

Company material

A shared folder the engine reads via the Drive connector.

  • Photos — rooms, property, dive/site shots → product images, hero/media
  • Ads / marketing instructions — campaigns, offers, channels → Growth sections + CRM/marketing setup
  • Company data — rate cards, menus, rosters, financial notes, decks
  • Brand kit — logo, colours, fonts
Drive folder (read) · mixed docs/sheets/images
4 · Company name & 5 · Key personnel

Identity & org

Anchors research, branding and the org/HR model.

  • Legal/trading name → company record, site title, footers
  • Owners & CEO-level (e.g. Edwin / Evan)
  • Department heads + self-managing structure
  • Named experts (e.g. dive instructors, GM) → org chart, HR employees, skills
name + people list → res.company, hr.employee, org chart
Secret handling. Odoo credentials and any Drive-sourced PII are treated as runtime secrets: passed via environment/MCP config, used only to authenticate API calls, and never committed to the generated repository. The engine emits a reminder to rotate the key/password after a run.

03Inside the box — the agent roster

An Orchestrator owns state and sequencing; it dispatches seven specialist agents and only advances a stage once that stage's verification passes. Each agent has a narrow mandate, its own tools, and an explicit "done-when".

🧭
Conductor

Orchestrator

Parses the brief, plans the run, sequences stages, holds shared state & created-record IDs, loops each stage until green, and escalates to a human on hard failures or approval gates.

tools: planning, state file, sub-agent dispatch · done-when: all stages green
🔎
Due diligence

Research Agent

Verifies the company, market, competitors and reputation from the open web + the Drive material; produces the fact base (with confidence flags) that every written section draws on.

tools: web search/fetch, Drive read · done-when: fact base + sources compiled
✍️
Narrative

Content Agent

Writes the 27 report sections + companion-page copy (Exec summary, PESTLE/SWOT/Porter, personas, workflows, roadmap, FAQ, sales page) honouring tone and the brief's guardrails.

tools: fact base, brand voice · done-when: all sections drafted & consistent
🎨
Frontend

Design / Build Agent

Renders the self-contained HTML: theme tokens, charts, BPMN/diagrams, nav, PWA, and responsive layout (0 horizontal overflow target). Produces the website + this page.

tools: HTML/CSS/JS, Chart.js, SVG renderer · done-when: renders, 0 console errors
🖼
Media

Asset Agent

Pulls photos & brand assets from Drive (and openly-licensed sources where gaps exist), processes/normalises them, and wires real images into the site and the Odoo product/room records.

tools: Drive read, image fetch/process · done-when: every product/room imaged
🏨
ERP build

Odoo Build Agent(s)

Connects to the instance and runs the 9-stage runbook: install apps/industries → company/tax/journals → master data → products & rooms → POS & booking → transactions → invoice/pay → automations → QA. Idempotent (search-before-create).

tools: Odoo MCP / XML-RPC, browser for SaaS activation · done-when: counts within ±10% of targets
🤖
Operational AI layer

Automation Agent

Configures the resort's own AI/automation layer inside Odoo — concierge, dynamic pricing, dive daily-briefing, overbooking guard, review responder, upsell, win-back — as scheduled/server actions + documented external-AI hooks.

tools: Studio automations, scheduled actions, AI hooks · done-when: actions exist & fire
✅
Quality gate

QA / Verification Agent

Renders pages headlessly (desktop + 390px mobile), checks for errors/overflow, runs cross-module Odoo spot-checks, and produces the build report (counts vs. targets, deviations).

tools: headless browser, search_read, diff · done-when: all verifications green

04How the box runs — gated, looped, idempotent

The engine never barrels ahead. Each stage is attempted, verified, and only then unlocked for the next — with bounded retries and human gates on anything irreversible or outward-facing.

Plan. Orchestrator reads the brief + inputs and writes a run plan: which sections, which Odoo apps, demo-data targets, and the approval gates.
Research. Research Agent compiles the verified fact base (company, market, competitors, reputation) with confidence flags; gaps are marked, not invented.
Generate website. Content + Design + Asset agents produce the report & companion pages; QA renders them and fixes errors/overflow before sign-off.
Reset & build Odoo. Build Agent safely clears old demo data (confirmed), installs apps/industries, then loads master data → products/rooms → POS/booking.
Transact. Generate bookings, dives, POS orders, invoices & payments across a realistic seasonal window; confirm/post in separate passes.
Automate. Automation Agent installs the operational AI layer (concierge, pricing, briefing, guards) — money/outbound actions stay human-approved.
Verify. QA Agent runs cross-module spot-checks + mobile renders; counts must land within ±10% of targets or the stage re-runs.
Ship. Commit the site, deploy to Pages, leave the live Odoo demo populated, emit the build log + a key-rotation reminder.

🔁 Idempotent

Search-by-natural-key before every create. Re-running a stage never duplicates records — safe to retry on failure.

🚦 Gated

A stage only starts when the previous stage's verification query is green. Bounded retries, then escalate rather than thrash.

🙋 Human-in-loop

Price changes, destructive deletes and outbound guest comms pause for explicit approval. Info-only steps run automatically.

08How to run it

The engine is driven inside Claude Code: background Agent tasks for each specialist, the /loop skill for verification cadence, and an Odoo MCP server (or XML-RPC) for the build. The full specification lives in the repo.

1 · Connect

Attach the Odoo MCP / credentials + the Google Drive connector. Hand the Orchestrator the brief, company name & personnel.

2 · Dispatch & loop

Orchestrator launches stage agents; /loop re-runs each stage's verification and advances only on green.

3 · Approve & ship

Approve the gated steps (pricing, comms, destructive resets); the engine commits, deploys and leaves the Odoo demo live.

Specifications: agents/orchestration.md (build loop & agents) · odoo-build-spec/mcp-runbook.md (9-stage sequence) · odoo-build-spec/automations.json (operational AI layer).
