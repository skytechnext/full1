AI Build Playbook

The modern (2026) best practices behind the Black Box — the agentic patterns that turn raw inputs into a finished website and a live ERP: loops, the harness, context engineering, RAG, goals, evals and guardrails. Closes with two alternate architecture variations and a recommendation.

Reflects current industry guidance from Anthropic, Google Cloud, LangChain, Mews and others (2026). Sources at the foot of the page.

01The agent loop & the harness

Every autonomous output engine is, at its core, one tight loop wrapped in a harness. The model doesn't "do" the work in one shot — it iterates: decide a next step, take an action through a tool, observe the result, judge whether the goal is met, and repeat. The harness is everything around that loop that makes it safe, grounded and repeatable.

🎯 Goal→ 🧠 Plan / decide→ 🛠 Act (tool)→ 👀 Observe→ 🔁 Reflect / verify↺

…loop until the verification for this step passes, then advance. Bounded retries; escalate on hard failure.

The loop

The reasoning cycle — ReAct (reason+act), planning and reflection. It owns "what next?" and "are we done?". Keep it bounded: a max-iteration cap and a clear success test stop runaway cost and goal drift.

The harness

The scaffolding around the loop: tool contracts, memory/context, retrieval, a policy/approval layer, and observability. A good harness means the same prompt produces reliable, auditable results run after run — not a clever one-off.

02The six-layer reference stack

The enterprise pattern that's emerged for production agents (2026). Each layer has one job; you can swap implementations without rewriting the others.

1 · Interface

Where requests enter — chat, API, a brief, a webhook. Normalises the ask into a goal the orchestrator can plan against.

2 · Orchestration

Task decomposition & planning; sequences stages, dispatches workers, holds state, loops until each stage verifies. The "plan-do-evaluate" brain.

3 · Tools

Strict, typed contracts for every action the agent can take (Odoo MCP/XML-RPC, web, file I/O, Drive). Narrow, well-described tools beat one do-everything tool.

4 · Memory & retrieval

Short-term scratchpad (within a run) + long-term memory (across runs) + RAG over the knowledge base. Context persistence is what stops the agent "forgetting".

5 · Policy & safety

Policy-as-code + human approvals for irreversible/outbound actions + prompt-injection defenses + data validation. Guardrails live here, not in prompts alone.

6 · Observability & eval

Trace every step, log every write, and run evals on full trajectories (tool choice + outcome), not just final answers. As autonomy rises, this layer matters more.

03Context engineering — what the agent knows at the moment of action

If prompt engineering is "how to ask," context engineering is "what does the agent know, see and remember when it acts?" In 2026 this is the discipline that most separates a demo from a dependable system.

🗒 Short-term memory

A run-scoped scratchpad: state checkpointed across every step so the agent can write a fact now and fetch it later. Compaction summarises old context when the window fills (this very engagement was compacted mid-build).

🧠 Long-term memory

Knowledge that survives the session — stored as files with per-write audit trails, shareable between agents in a workspace. Lets one run learn from the last instead of starting cold.

🛠 Tool design as context

Tools are part of the context budget. Give the model context-awareness (how much budget remains), prefer programmatic tool-calling for fan-out, and write crisp tool descriptions — the model only acts as well as its tools are described.

Rule of thumb: curate context, don't dump it. Retrieve the few facts a step needs, summarise the rest, and keep tool outputs tight. Most agent failures are context failures — wrong, missing, or stale information at the moment of action.

04RAG — grounding the engine in real facts

Retrieval-Augmented Generation feeds the model real, current information (the company's docs, rates, photos, the live web) instead of trusting it to remember. The 2026 move is from a fixed pipeline to a control loop — and to routing each query to the cheapest pipeline that can answer it.

Classic RAGRetrieve top-k once → generate. Predictable, simple.Simple, low-error-tolerance Q&A (FAQ, policy)~$0.001/query · fast
Agentic RAGThe model decides when/how to retrieve, can decompose, retry & cross-check sources inside its reasoning.Complex tasks needing retries, decomposition, multi-source verification~10× cost · +seconds
Adaptive RAG 2026 defaultA classifier routes each query by complexity — simple → classic, hard → agentic/graph.Mixed workloads — keeps cost low, scales effort only when neededcost matches complexity

Governance precedes retrieval. Enterprise RAG fails without access controls, metadata and provenance on the corpus. Ground every claim, carry source + confidence, and never let the model invent what it can't retrieve — exactly how the report flags unverified facts.

05Goals, planning & the core patterns

Start with the simplest pattern that fits — most teams over-architect. Compose these as needed.

ReAct

Reason → act → observe in a loop. The baseline for tool-using agents.

Planning

Decompose a known multi-step task up front for predictable execution.

Reflection

The agent critiques and improves its own output — use when quality is the bottleneck.

Orchestrator–Worker

A planner decomposes & assigns; workers focus on one step. Only the orchestrator sees the whole.

Watch goal drift. Over many iterations a refined plan can wander from the original intent, and backtracking burns compute unpredictably. Pin the goal, verify against it each stage, and cap retries.

06Evals & guardrails — non-negotiable

✅ Evaluation

  • Evals are not optional; test full trajectories (tool choice + outcome), not only the final answer.
  • Per-stage verification queries gate advancement (counts within tolerance, renders clean, spot-checks pass).
  • Observability: trace steps, log every write, measure cost & latency per run.

🛡 Guardrails

  • Policy-as-code + approvals for irreversible actions (destructive resets, price changes, outbound comms).
  • Prompt-injection defenses & input validation — treat retrieved/external content as untrusted.
  • Secrets as runtime config, never committed; least-privilege tool scopes; rotate after use.

07Two alternate architecture variations

The same playbook can be assembled in different ways depending on budget, scale and how much exploration the task needs. Below: the recommended baseline plus two alternate variations. The right choice is the simplest one that meets the quality bar.

Recommended for Casa Escondida

Baseline · Centralised loop

A single orchestrator running a ReAct loop with adaptive RAG and a fixed stage runbook. The Black Box as built today.

TopologyCentralised orchestrator
RetrievalAdaptive RAG
MemoryScratchpad + run log
Cost / complexityLow
Covers~80% of cases

Best when the workflow is known (build a site + an ERP). Predictable, cheap, easy to debug.

Variation A

Lean · Single-agent micro-harness

One capable agent, classic RAG, tight tool set, no sub-agents. Minimal moving parts.

TopologySingle agent
RetrievalClassic RAG
MemoryShort-term only
Cost / complexityLowest
Trade-offLess parallelism / depth

Best for a fast, low-cost build or a constrained instance. Cheapest to run; weaker on large fan-out research and self-correction.

Variation B

Scale · Hierarchical multi-agent

Orchestrator + specialist swarm, reflection inside each worker, graph/agentic RAG, long-term shared memory.

TopologyHierarchical swarm
RetrievalAgentic / Graph RAG
MemoryLong-term, shared
Cost / complexityHigh
Trade-offMore coordination overhead

Best for many properties / continuous operation / deep research. Highest quality & throughput; needs strong observability to manage goal drift & cost.

Recommendation. Build on the Baseline for a single resort like Casa Escondida — it already delivered this website and the live Odoo demo. Drop to Variation A if you need the cheapest possible refresh; graduate to Variation B only when running the engine across a portfolio of properties or operating the resort's AI layer continuously, where its shared memory and parallelism earn their extra cost.
